# Architecture

neuraldoc is one Node.js process. It serves the React interface, a small REST API and an MCP endpoint, and keeps its state in a folder on disk. There is no database server and no background worker.

```
                    ┌──────────────────────────── container ──────────────────────────────┐
 browser ──/app/──► │  frontend/dist        React + TanStack Router + shadcn/ui           │
                    │                                                                     │
 browser ─/api/mcp► │  mcp/serve.mjs ──► mcp/handler.mjs ──► projects.mjs  (own project)  │
 agent ────/mcp───► │                                    └─► core.mjs      (showcase)     │
                    │                                                                     │
                    │  /data  projects, decisions, draft and Jev caches                   │
                    └──────────────────────────────────┬──────────────────────────────────┘
                                                       │ HTTPS, only on request
                                          Jev, LLM provider, GitHub (clone, pull requests)
```

## Two images, one interface

| Image | Data | Model calls |
|---|---|---|
| **App** (`docker build .`, default target) | Empty until you import an uploaded or cloned repository, optionally with separate documents. **Beispielprojekt laden** clones the MOBIQ sample ([mobiq-code](https://github.com/neuraldoc-ai/mobiq-code), [mobiq-docs](https://github.com/neuraldoc-ai/mobiq-docs)) like any other project. | Your LLM and Jev for the initial check, only on explicit click |
| **Showcase** (`--target showcase`, `NEURALDOC_MODE=showcase`) | The prepared MOBIQ example from the `datasets/` submodules | none; prepared drafts are shown, import is off |

The app image contains no sample data: without `datasets/`, [`vite.config.ts`](frontend/vite.config.ts) builds everything that belongs to the showcase from an empty stand-in, and the server loads the showcase modules (`core.mjs` and friends) only in showcase mode. Both use the same pages and components: [`features/docs/data.ts`](frontend/src/dashboard/features/docs/data.ts) exports the active dataset (empty, an imported project, or the showcase fixtures loaded as a separate chunk), and [`main.tsx`](frontend/src/dashboard/main.tsx) installs it before the pages load. Before the first import every data page shows the start screen ([`empty-start.tsx`](frontend/src/dashboard/features/docs/empty-start.tsx)). The interface never branches into a second copy of a page.

## Pipeline for your own project

1. **Upload** ([`upload.ts`](frontend/src/dashboard/features/docs/upload.ts), [`mcp/project-upload.mjs`](mcp/project-upload.mjs)). The browser reads a dropped or picked folder or ZIP, filters it with the shared rules in [`import-rules.mjs`](frontend/src/dashboard/features/docs/import-rules.mjs) (code and documents only; no `node_modules`, build output, lock files or secrets; nothing the folder's `.gitignore` files exclude) and sends one ZIP: `repo/…`, `docs/…` and a manifest. A dropped ZIP is read as a stream and only the entries the rules keep are decompressed, so a ZIP of a whole working folder with its dependencies (135 MB, 30,000 files) is reduced to its code and documents (under 1 MB) in about a second; Windows ZIPs with backslash paths are normalised first. A GitHub URL in the manifest is cloned on the server with `git clone --depth 300` over https only. Extraction rejects path traversal and oversized archives and never unpacks a `.git` folder: an upload has no history (its Git config could make the history reader run commands), only a clone by URL does, and the history reader runs `git show` without external diff tools or text conversion.
2. **Import** ([`mcp/project-import.mjs`](mcp/project-import.mjs), [`mcp/doc-text.mjs`](mcp/doc-text.mjs)). Classifies files again on the server. Without a documentation upload, READMEs, `docs/` folders and PDF/Office files in the repository count as documentation; licences, changelogs, templates and test fixtures do not. PDF (pdf.js), Word, Excel and PowerPoint (their XML) and Confluence pages in storage format become text. Documents are split into one section per heading (levels 1 to 4); a section of a heading and a line or two is merged into the next one, a long one is cut at a blank line of at most 6,000 characters, and a code block is never cut (it may make its section up to three times as long). Each section is an exact slice of the original, so the export can put approved text back. Sections without prose (logos, badges, a list of links) are marked as not checkable. The dashboard shows a document as one page with its sections as blocks. A cloned repository's history ([`mcp/git-history.mjs`](mcp/git-history.mjs)) is read from the newest tag on (without a tag: 90 days): commits, merge requests parsed from GitLab and GitHub merge messages, and every commit's diff (stored next to the project in `diffs.json`, the clone is deleted). Merges on the main line become features with the commits their branch brought in; other commits are grouped by ticket key; features that change no code are left out. Each commit gets a kind of change from its files (tests, fix, rename, database, parameter, UI, process), which decides the feature's nature.
3. **Code graph** ([`mcp/code-analysis.mjs`](mcp/code-analysis.mjs)). Tree-sitter (WASM) for Java, Kotlin, TypeScript/TSX and Pascal, the TypeScript compiler for symbol resolution, `pgsql-parser` for SQL. Unresolved or dynamic calls stay open instead of being guessed.
4. **Initial check** ([`mcp/check.mjs`](mcp/check.mjs), [`mcp/projects.mjs`](mcp/projects.mjs)). Runs in the background (`POST /api/mcp/project/check` starts it, `GET` reports the phase and how many sections are done), three sections at a time.
   - *Terms and code places.* The names a section mentions (code spans, identifiers, flags, environment variables, endpoints; in code blocks only code, not comments or strings) are looked up in an index of every identifier in the code, so the model learns which names occur where and which occur nowhere. The code is cut into excerpts of about 60 lines; they are ranked by BM25 (English and German stemming, camelCase split) plus the rarest section names they contain, and every file the section names by path or unique file name comes first. Up to 14 excerpts within 28 KB (more for a section that walks through many files), at most three per file and one from tests or scripts. A section that states many values (at least three numbers or six names written like code: a table of settings, a list of limits) states more facts than these excerpts cover, so its facts also get their exact places: for each name written like code, the lines that use it (product code first, lines with a fallback or default first); for each number, the lines that set a number next to the same words (`1,500 code files` → `codeFiles: 1500`, `the last 90 days` → `--since=90.days`), weighted by how rare the shared words are. At most ten of each, three lines apiece.
   - *Values and the history* ([`mcp/change-facts.mjs`](mcp/change-facts.mjs), no model). Lines of code are read as name–value pairs (`NAME || .5`, `rows: 500`, `'--depth', '300'`, `get('NAME', 10)`). For a repository imported by URL, the diffs of the commits since the last release show which values and names changed (`rows: 1000 → 500`, `APP_GIT_TOKEN → APP_GITHUB_TOKEN`); a section that still states the old value next to the name (or its words: `rows`, `code files` for `codeFiles`) or the old name gets the change and the current line as a hint, and only those sections get a different request. A change the proposed text still states in its old form (the model missed it, or the review dropped the finding) becomes a question to the reviewer with the commit ("Gilt jetzt 0.5?"). A constant or flag that product code sets to different values in different places (examples and tests left out), while the section states one of them, becomes a question to the reviewer ("Welcher Wert gilt?") unless a finding already corrects it: guessing the place is how a changed default slips through.
   - *Findings.* Your LLM (default `gemini-3.5-flash-lite` with thinking level medium) works in three passes: every statement against the code (*contradicts*), every list of names against its definition (*missing*), every name that occurs nowhere (*removed*, only where an excerpt shows where it would have to be). In a section that states many values it first lists every single fact (a table row with a name and a default is two facts, each list gets a "complete?" entry) with a verdict (*matches*, *contradicted*, *not shown*), so that it does not stop after the first contradiction; prose and tables of terms are checked without that list, which there crowded out missing entries. Each finding has a literal quote from the section, a literal quote from an excerpt (for *removed*: the missing names), a German explanation for the reviewer and the line edits that fix exactly this finding.
   - *Server checks* ([`verifyFindings`](mcp/check.mjs)). A finding is dropped unless its quotes exist; a *removed* name must be a product name of the section (camelCase, CONSTANT_CASE, a flag, a member or call; never an example value, a commit hash or another tool) and must occur in no uploaded code file. Edits must be valid; a replacement is cut down to the lines that actually change; whitespace or emphasis alone is not a change; list markers, blank lines and code formatting of the original are kept; the language may not switch; source code may not be pasted into prose; findings may not overlap; more than 60 % of a long section is never rewritten.
   - *Second look.* The same model reviews the remaining findings of a section skeptically and drops context mistakes: another server, folder or entry point, an example or placeholder, a claim that rests on something not being in the excerpts, a mere alias or rewording. Measured: on neuraldoc's own documentation it removed 7 of 7 wrong findings (and 2 of 10 correct ones), on the API documentation of the benchmarks it lost nothing.
   - *Completeness per document.* A document that lists names of one kind (options, environment variables, settings, fields, methods) spreads them over many sections. The excerpts that define most of the document's names (a settings file, an options interface; whole files while they fit in 32 KB) are compared with the document: names there that no document mentions, written like the documented ones and in a definition position, go to the model, which decides for each one whether to add it, where, and in the format of the neighbouring entries. Environment variables are read all over the code rather than defined in one place: constants that share a prefix with at least three documented names (`NEURALDOC_…`) and that no document mentions are candidates too, first, each with the line that reads it.
   - *Jev* ([`verifyWithJev`](mcp/check.mjs)) rates every finding as *confirmed*, *refuted* or *unclear*. A clear refutation (0.75, confidence 0.6) drops the finding, a confirmation (0.7) marks it "von Jev bestätigt"; a deletion needs that confirmation, because dependency folders are never uploaded and a name can live there. A malformed Jev answer is retried once; then the findings stay unconfirmed.
   Every section with a finding becomes a proposal that already carries its corrected text and its findings; a section the code cannot decide becomes a question. Model answers are cached by content in `check-cache/` (shared by all projects), Jev answers per project; a repeated check costs nothing. Rate limits (HTTP 429) are retried with backoff; a wrong key ends the check, a single failing section does not.
5. **Re-checking one section** (`POST /api/mcp/drafts/generate` with the reviewer's answer) runs the same section check with the answer added to the input. [`mcp/drafting.mjs`](mcp/drafting.mjs) and [`mcp/draft-prompt.mjs`](mcp/draft-prompt.mjs) keep the provider calls, the price list and the showcase drafts. See [mcp/DRAFTING.md](mcp/DRAFTING.md).
   [`mcp/project-features.mjs`](mcp/project-features.mjs) turns the features into the same changes the showcase has. Commit subjects say little to someone who keeps documentation, so the initial check first describes every feature in plain German ([`mcp/feature-texts.mjs`](mcp/feature-texts.mjs), one cached call per feature, about 0.003 USD): a title for what is different now, one or two sentences on who notices it, the kind (*Neue Funktion*, *Geändertes Verhalten*, *Fehlerbehebung*, *Intern*) and the parts of the product it touches, read from the commit messages and the diff (product code first, tests and lock files last). Until then the title is the subject without its conventional prefix and the kind comes from the prefix. The pages of an own project show its own documents (README.md, docs/…) instead of the showcase's doc types. A proposal belongs to the feature whose changed files overlap most with the code excerpts its section contradicts (the newest on a tie); findings no commit since the last release explains stay in „Weitere Abweichungen“. This is derived when the project is read, so a later check needs no re-import.
6. **Review and export** ([`section-review.tsx`](frontend/src/dashboard/features/docs/section-review.tsx), [`markdown.tsx`](frontend/src/dashboard/features/docs/markdown.tsx), [`line-diff.ts`](frontend/src/dashboard/features/docs/line-diff.ts)). The editor renders a section as Markdown with its changes in place: a changed line stays one line with only the changed words marked (code spans and links are compared as one piece, whitespace never counts), removed lines are struck through, added ones green, each change numbered; below it every number has its reason and code quote. Unticking a change applies the others only (the same line-edit rules as the server); the result is stored as an edited approval. Decisions are stored per project. The export merges approved sections into their documents (PDF, Office and HTML as Markdown) and adds `neuraldoc-export.json` with the SHA-256 of each original.
7. **Pull requests on GitHub** ([`mcp/github.mjs`](mcp/github.mjs), [`github-publish.tsx`](frontend/src/dashboard/features/docs/github-publish.tsx), [`settings/github.tsx`](frontend/src/dashboard/features/settings/github.tsx)). With a GitHub App (created from a manifest in Einstellungen; pull requests by `<app>[bot]`, commits signed by GitHub) or a personal token, approved sections become a pull request, the way Dependabot or Renovate work. A repository imported by URL is the target of its documents; an uploaded folder, or documentation in another repository, gets its repository on the overview. After every approval or withdrawal (debounced, or on a button with `NEURALDOC_GITHUB_PR=manual`) the server reads each affected file from the base branch through the API, puts the approved sections in where their original text still stands (CRLF and BOM kept; a section changed there meanwhile is a conflict and stays out). A Confluence page in storage format ([`mcp/confluence-storage.mjs`](mcp/confluence-storage.mjs)) was Markdown only for the check: every changed line is reduced to the words that changed and replaced inside the one text node it comes from, searched from where its section begins; markup, macros and attachments stay byte for byte. New or deleted lines, changes across formatting and the page title are listed in the pull request instead (on the MOBIQ documentation every body line maps back exactly), and writes one commit on top of the base through the Git Data API: tree, commit, branch `neuraldoc/docs` (or one branch per document) moved with force. Nothing is cloned and the base branch is never written. The pull request is opened (labels, reviewers, draft) or updated; its body lists every section with reason, finding, code evidence and who approved it, and what could not go in (PDF and Office files, conflicts, parts of a Confluence page). Every commit carries `Generated-by: neuraldoc`; a branch whose newest commit lacks it was changed by a person and is left alone until „Branch neu aufbauen“. A pull request with nothing left to carry is closed and its branch deleted; one closed on GitHub stays closed while the approvals are the same. Merged pull requests publish their sections: they show „PR #n gemergt“ and can no longer be withdrawn. State lives in `github.json` (records per repository and branch, published sections, repository overrides per project).
8. **Comments inside the code** ([`mcp/comments.mjs`](mcp/comments.mjs), [`mcp/comment-check.mjs`](mcp/comment-check.mjs); command line only so far: [`mcp/comment-check-cli.mjs`](mcp/comment-check-cli.mjs)). Comment syntax by file type (no parsers) marks every line as code, comment or trailing comment; comment blocks (no licence headers, directives or commented-out code) get the code they describe. Files are checked in windows of about 200 lines (`NEURALDOC_COMMENT_WINDOW`). Before any model call the server looks for documented parameters a signature lacks, Go doc comments that name another function and names in comments that no code line has. The model sees the window, these signals next to their comment and related code (definitions of names a comment mentions, places that read a documented option or field, called functions, then BM25 excerpts), once with a verdict per comment block and once findings only; the union is verified (quote inside a comment, evidence in code lines, the correction still a comment) and reviewed a second time. Measured in [mcp/eval/README.md](mcp/eval/README.md#comments-inside-the-code-6-october-2026).

## Showcase

[`mcp/core.mjs`](mcp/core.mjs), [`mcp/sources.mjs`](mcp/sources.mjs) and [`mcp/impact.mjs`](mcp/impact.mjs) read GitLab, Jira, Confluence, SharePoint and PostgreSQL data of the MOBIQ dataset and answer the three MCP tools from it. Prepared proposals come from [`showcase-data.ts`](frontend/src/dashboard/features/docs/showcase-data.ts), which Node 24 loads directly as TypeScript; [`mcp/showcase-init.mjs`](mcp/showcase-init.mjs) installs it into `data.ts` before these modules run. Words shared by both images (document types, change kinds) are in [`vocabulary.ts`](frontend/src/dashboard/features/docs/vocabulary.ts). The ground truth in `datasets/mobiq` is used only by tests, never by the MCP. Details: [docs/mobiq-showcase.md](docs/mobiq-showcase.md).

## HTTP surface

| Path | Purpose |
|---|---|
| `/app/*` | The interface (single-page app) |
| `/mcp` | MCP over JSON-RPC 2.0, Streamable HTTP with JSON responses |
| `/api/mcp/project`, `/import` (ZIP body), `/activate`, `/export` | Own projects |
| `/api/mcp/project/check` | `POST` starts the initial check in the background, `GET` reports its phase, progress and errors |
| `/api/mcp/project/source`, `/commit?sha=`, `/documents` | Repository with history, one commit's diffs and the full documents for the Daten page |
| `/api/mcp/github/status`, `/sync`, `/test`, `/target`, `/app/manifest`, `/app/callback` | Pull requests on GitHub: state of the active project, sync now (`force` rebuilds a branch a person changed), connection test, repository per project, creating the GitHub App from a manifest |
| `/api/mcp/db/connections`, `/connections/delete`, `/test`, `/query` | Own PostgreSQL connections ([`mcp/db-connections.mjs`](mcp/db-connections.mjs)): stored without returning the password, every query in a read-only transaction over the extended protocol (one statement), 15 s and 1,000 rows |
| `/api/mcp/drafts`, `/decisions`, `/changes/:id`, `/usage`, `/activity`, `/setup` | Drafts, decisions, statistics, configuration status |
| `/health/live` | Liveness probe used by the Docker healthcheck |

Write requests must come from the same origin or carry the MCP token. The server is meant for local use: there is no user management and the demo token is no protection on a public network.

## State

Everything lives below `NEURALDOC_STATE_DIR` (`/data` in Docker, `mcp/state/` otherwise): `projects/<id>/project.json` with code, document texts, sections and Git history (`diffs.json` next to it), `active.json`, `connections.json` (mode 600), `github.json` (pull requests neuraldoc keeps), decisions, MCP logs, the Jev and draft caches, and `check-cache/` with the model answers of the initial check (content-addressed, shared by all projects, deleted with **Zurücksetzen**). Uploads are unpacked into a temporary folder there and deleted right after the import. Deleting the folder resets the app. Busy locks for import, check and drafting are per process.

## Logging

[`mcp/log.mjs`](mcp/log.mjs) writes one line per event to stdout/stderr, so `docker logs` and Docker Desktop show it: start and configuration (Jev key and LLM provider present or missing), uploads and clones, import results, check progress and costs, drafts, every write request and every failed request with its cause. Programming errors are logged with their stack. Keys, document text and code never appear in the log.

## Adding a language

Code analysis is in [`mcp/code-analysis.mjs`](mcp/code-analysis.mjs). A new language needs a tree-sitter WASM grammar (the project uses `@lumis-sh/wasm-*` packages), the queries for functions and calls, and the file extension in the importer's `CODE` pattern. Add a fixture to [`mcp/code-analysis.test.mjs`](mcp/code-analysis.test.mjs). Without call resolution, files of that language are still imported as sources.
